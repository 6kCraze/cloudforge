# V2 failure matrix

Validated on 2026-09-26 against PostgreSQL 17 and RabbitMQ 4 using the local Docker Compose environment. “Automatic” means recovery occurs after the dependency returns while the affected process is still running. A process that exits during initial database connection needs an operator or process supervisor to restart it.

PostgreSQL is the lifecycle authority throughout this matrix. RabbitMQ Ready and Unacked counts describe delivery state; they are not job states.

## Behavior and persisted state

| # | Initial state and action | Expected behavior | Actual behavior and evidence | PostgreSQL state | RabbitMQ state |
|---:|---|---|---|---|---|
| 1 | API is running; PostgreSQL is stopped; submit a job. | Reject the request and report no durable acceptance. | Observed HTTP 500; the API did not return a job ID or `202`. A later request can succeed after PostgreSQL returns. | No job or outbox row is committed. | Unchanged; the API never publishes directly. |
| 2 | PostgreSQL and API run; RabbitMQ is stopped; submit a job. | Return `202` after the database transaction commits; retain publication intent. | Observed job `ea2b6ad6…` accepted while RabbitMQ was down. Dispatcher retried with capped backoff and completed the flow when RabbitMQ returned. | `queued`, attempt 0, matching outbox `published_at = NULL` until recovery; later `succeeded`, attempt 1. | No message while down; one persistent message after reconnect, then ACKed. |
| 3 | Dispatcher is stopped; API, database, RabbitMQ, and worker run; submit work. | Jobs and outbox events commit but do not publish until dispatcher returns. | Observed job `fc61feb7…` remain queued and unpublished. Restarting the dispatcher published the retained event. The system integration test repeats this boundary. | `queued`, attempt 0; outbox NULL until dispatcher starts. | No new message before dispatcher; Ready after publication. |
| 4 | A committed unpublished event exists; dispatcher stops before publish. | The event remains eligible and publishes after restart. | Verified by stopping the dispatcher before creating job `1a0d4904…`; it survived the full restart and published afterward. | Job and NULL `published_at` persist. | No message before publish; Ready afterward. |
| 5 | RabbitMQ confirms a publish; dispatcher does not record `published_at`; run dispatcher again. | The same event may publish twice; neither notification may execute the job twice. | `TestConfirmedButUnrecordedEventCanBePublishedTwice` produced two notifications with the same message ID. Worker duplicate tests kept `attempt_count = 1`. | Event can remain NULL despite one broker copy; later mark succeeds. Job becomes terminal once. | Two copies can be Ready or delivered; both share the outbox UUID. |
| 6 | Dispatcher runs; RabbitMQ becomes unavailable. | Leave events unpublished and reconnect with bounded backoff. | Observed retry delays grow to their cap. | 7 | A persistent message is Ready in the durable queue; restart RabbitMQ. | Exchange, queue, binding, and Ready message survive. | Observed Ready=1 before and after `docker compose restart rabbitmq`; durable queue and `job.ready` binding remained. | 8 | Worker is stopped; dispatcher publishes jobs. | Jobs remain queued; Ready grows; starting worker drains the queue. | Observed in the full-path test and live restart test. | 9 | Worker stops before RabbitMQ delivers a Ready message. | No claim occurs; another worker can receive it later. | Same broker state as worker downtime; real system test showed the job unchanged until the consumer started. | Remains `queued`, attempt 0. | Message remains Ready; no Unacked delivery. |
| 10 | Worker receives a delivery, then its channel/process dies before database claim. | Broker requeues/redelivers; replacement worker may claim normally. | RabbitMQ integration tests close a consumer without ACK and observe `redelivered=true` with the same message ID. Claim-by-ID remains conditional. | Still `queued`, attempt 0 until replacement claims it. | Unacked returns to Ready, then is redelivered. |
| 11 | Worker receives and claims `queued -> running`, then crashes before terminal persistence. | Current V2 must avoid unsafe re-execution and expose the stuck job. | `TestUnackedDeliveryIsRedeliveredAndRunningJobIsNotReexecuted` observed redelivery; replacement ACKed without execution. | Remains `running`, attempt 1, original `claimed_by`; no terminal timestamp. | Original Unacked is redelivered, then ACKed by replacement. |
| 12 | Worker persists `succeeded`, then crashes before ACK. | Redelivery consults PostgreSQL, skips execution, and ACKs; attempt stays one. | `TestSucceededJobRedeliveryIsAcknowledgedWithoutReexecution` observed `redelivered=true`, one execution, and attempt 1. | `succeeded`, attempt 1. | Unacked is redelivered; duplicate is ACKed and removed. |
| 13 | PostgreSQL fails while a worker handles a delivery. | Do not ACK completion; NACK/requeue and slow retries. | Live test exposed an initial hot reconnect loop. | 14 | RabbitMQ fails while worker is connected. | Connection closes; unacknowledged delivery is requeued by RabbitMQ; worker reconnects. | Connection/reconnect behavior is covered by `TestWorkerReconnectsAfterConsumerFailure`; crash-window integration tests prove unacknowledged redelivery. | 18 | Deliver a valid message containing an unknown job UUID. | PostgreSQL proves no work exists; log and ACK/drop. | Integration test delivered an unknown UUID, then successfully processed a valid job with the same consumer. | No job row exists or changes. | Unknown delivery is ACKed and removed. |

## What the matrix proves

- A `202 Accepted` job and its publication intent survive broker and application outages because they commit together in PostgreSQL.
- RabbitMQ durability protects topology and persistent Ready messages across the tested clean broker restart.
- Publisher confirms prevent CloudForge from marking an unaccepted or unroutable event published, but cannot remove the confirmed-before-recorded duplicate window.
- Manual ACK protects a delivery until durable handling, while PostgreSQL prevents completed-job redelivery from executing twice.
- V2 favors visible stuck `running` state over guessing after ownership is lost. It has no automatic abandoned-job recovery.
